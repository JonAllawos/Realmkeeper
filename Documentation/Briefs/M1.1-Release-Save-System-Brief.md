PRIMARY OBJECTIVE

Turn the "many seeded worlds" front end into the release shape of a single-player RPG:
New Game, Continue, Load Game, Save Game, Settings, Exit Game; three manual save slots; autosaves at safe moments; backups and recovery from a bad or interrupted save; and slot details a player can recognise (character, level, place, playtime, picture).

This is the smallest step that changes the product's shape. It needs no story canon.

⸻

2. SLOTS

| Slot names | Written by | Kept |
|---|---|---|
| slot-1, slot-2, slot-3 | The player: Save Game | Until overwritten (confirmation) or deleted (confirmation) |
| auto-1, auto-2, auto-3 | Autosave | Rotating: the oldest is replaced |

- Each file keeps one backup, <slot>.rkworld.json.bak, made by the atomic replace.
- Older slots (autosave, world-named slots) are listed in development builds only, under "Other saves". They load and migrate as today.
- Known limitation (accepted): the autosave rotation is shared, so a second playthrough's autosaves can replace the first's. Its manual slots are never touched.

⸻

3. LOAD GAME AND SAVE GAME SCREENS

Each slot card shows:
- character name, class and level;
- location (settlement, place, or region's country);
- in-game date and time;
- playtime;
- the real time it was last saved;
- a thumbnail;
- a compatibility state: Ready / Will be updated (older version) / Too new for this build / Damaged (backup available) / Damaged.

Actions: Load, Delete (confirmation), and Save here (Save Game only; confirmation when the slot is used). Damaged with a backup offers "Load backup", which restores the backup into the slot only after it loads successfully. Keyboard and controller navigation follow the Phase 25 design system; captures from 1024×768 to 3440×1440.

⸻

4. CONTINUE

- Picks the save with the newest playedAtUtc in its header (not the file time), among Ready and Will-be-updated saves, across manual and autosave slots.
- If the load fails, says so in plain words and offers the next newest. It never deletes or overwrites anything.
- In a game, Continue remains Resume.

⸻

5. NEW GAME

- Creates the world with a fixed name and seed held in one place in code (a stand-in for the canonical world definition until M1.3; values chosen by the owner, default the current test world, seed 123456789).
- Asks which slot to use. If it is occupied, it confirms. The occupied save is only replaced at the first save, and its file stays as the .bak.
- The character creation flow is unchanged: decision D4 (creation before play) belongs to M3.
- The founding save goes to the chosen slot, as CreateWorld does today.

⸻

6. SAVE FORMAT v28

Additions to the envelope, beside schemaVersion and savedAtUtc, readable without parsing the world:
- summary: characterName, className, level, locationText, minuteOfDay, date, campaignChapter (optional), playtimeSeconds, playedAtUtc, slotKind (manual or auto).
- integrity: a checksum (SHA-256) over the serialized world, so a truncated or edited body is detected before full deserialisation.

In the world:
- a playtime counter (seconds of active play; paused time and menus excluded).

Thumbnail: <slot>.jpg beside the save (about 320×180), written after the save succeeds. A missing or broken thumbnail never makes a save invalid.

Migration v27 → v28: structural. Playtime is unknown (0, shown as "—"); the summary is filled on the next save. A test loads a real v27 file and checks it is identical apart from the new fields.

ADR-0123 records the slots, the summary, the checksum and the v28 step.

⸻

7. RELIABILITY

- Backups: File.Replace with a backup path; a new slot has no backup until its second save.
- Interrupted saves: at start-up, a stale <slot>.rkworld.json.tmp is removed and logged. The old save and its backup are untouched.
- Corruption: a header that fails, a checksum mismatch, or a failed deserialisation marks the slot Damaged. The backup is offered when it verifies.
- Disk full or access denied: the save fails with a plain message, and the previous save is intact.
- Tests inject a failing writer (throw mid-write, truncate, deny) through the store's existing seams. Add a seam if none exists.

⸻

8. AUTOSAVE (M1.1 part)

Autosave writes to the rotation:
- right after a loading transition completes (arrival in a settlement, place, the country or a new region), still behind the loading screen;
- after a campaign decision or chapter change is recorded;
- on Exit Game and Return to Title (after the existing confirmation).

Never:
- during a fight;
- while a conversation is open;
- during a transition before it completes;
- while a command is applying;
- in the first 60 s after any save.

A setting turns autosave off (default on).

**Moved to M1.2:** the 10–15 minute timed autosave. A save currently stalls the main thread for about 0.6 s at 9 regions (Phase 30 measurement), so timed saves wait for M1.2's off-thread saving. M1.1 records the measured cost of each autosave in the log.

⸻

9. TESTS (focused)

- Save, load, overwrite (confirmed) and delete for each manual slot; Save Game refused in a fight and in a conversation, with the reason.
- Continue: picks the newest played; skips Too-new and Damaged; falls back on a failed load; never alters files.
- New Game with three full slots: no file changes until the founding save; the replaced save becomes the .bak.
- Failing writer: the old save and the .bak survive every injected failure; a stale .tmp is cleaned.
- Checksum: a truncated file and a one-byte edit are both Damaged; the backup restores.
- Migration: real v27 save → v28, identical apart from the new fields; the oldest supported save still loads.
- Autosave: fires at each trigger; never fires in the forbidden states; rotation keeps three.
- Playtime: advances in play, not while paused or in menus; survives save and load.
- Menu and screens: PlayMode in the shipped scene; captures at the Phase 25 width classes.
